# P1: Discover (requirements)

Use the `interview-me` skill if it is installed (one question at a time), and `idea-refine` if the idea is still vague. Otherwise interview directly: one question per message, multiple-choice where possible.

Find out:
- the problem, who has it, and what they do today;
- the users and their devices (this feeds P2);
- the core outcome, MVP boundary, non-goals, and success metrics;
- constraints: deadline, budget, compliance, sensitive data, accessibility, performance, offline use.

If the user names a reference app, site or bot ("like X"), research how it works before writing requirements: `phases/RESEARCH.md`.
An existing PRD with its own ID scheme is adopted, not rewritten (`phases/FIT.md`).

Standard tier and above: first write `docs/intent.md` from `templates/intent.md`, one page covering:
- the intent;
- v1 scope and what is out of scope;
- the decisions taken in the interview;
- facts to verify.

**Have the user confirm it** before writing the PRD. The PRD expands the intent and never contradicts it.

Write `docs/prd.md` from `groundwork/templates/prd.md`:
- give every requirement a stable ID (`REQ-001`, `JRN-001`, `NFR-001`) so later docs, tasks, and tests can link to it;
- give every REQ a testable acceptance criterion, in EARS (`WHEN <trigger>, the system SHALL <response>`; also `WHILE`, `IF … THEN`) or Given/When/Then. One need per row. `gw lint` flags rows without one, over-long rows and duplicate IDs;
- a row that is out of scope says so (`out of scope`, `deferred`): it then needs no task or test;
- mark unknowns with `[NEEDS CLARIFICATION: question]`. GATE 1 fails while any in-scope marker remains.

Small tier, new project: no separate PRD. Put the problem, 3–7 REQs and the non-goals at the top of `docs/plan.md`. A change to an existing project skips P1: its requirements go in the change folder (`phases/CHANGE.md`).
`gw phase P1 done`.
