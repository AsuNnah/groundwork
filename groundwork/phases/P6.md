# P6: Plan → GATE 1

1. `docs/plan.md` (`templates/plan.md`) when `gw docs` lists it (a change keeps its plan in `proposal.md`): milestones, risks, **Complexity Tracking**. Decisions, not code.
2. **Tasks**, in build order: `gw task add T01 "<title>" --verify "<command>" --req REQ-001,SEC-002` (change the IDs later with `gw task req T01 …`). Each task:
   - has a `verify` command that runs on THIS host's dev method;
   - is 15–60 minutes of agent work, about 400 changed lines at most (`diff_budget`: small batches), with exact files;
   - covers its REQ/SEC IDs (`gw trace`), and the test that proves it names the ID, e.g. `test('REQ-003 exports CSV', …)`.
   Optional fields in `.groundwork/tasks.json`: `files`, `depends_on`, `test_first`, `tier` (S0–S3), `parallel` (true when the task shares no files with the tasks beside it and needs only finished ones; at large tier P7 may give it to a worker), `role` (whose brief fits it: `gw team`).
3. `docs/test-strategy.md` when `gw docs` lists it: per target, which tests run at which tier (S0–S3) from the pack's `sandbox` and `test_tooling`, the coverage bar, the CI matrix for S3.
4. **Pre-build checks**, each passed or justified in Complexity Tracking: mockup approved in `docs/dbd.md` (UI targets); the fewest projects, services and dependencies; proven open-source parts reused where they fit (`phases/REUSE.md`); nothing "for later"; real DB and services in tests where practical (S1); a verify path at every target's release tier; SRD items mapped to tasks.
5. **Consistency pass:** intent, PRD, mockup and tasks agree (every REQ has a task, every task a REQ, every screen built is in the mockup). Run `gw lint` and `gw trace`. Ask the user about each conflict you can't settle as a two-option question ("CSV dates in UTC or local time?").
6. `gw gate G1`; fix what it lists.
7. **One review packet, one approval:** in one message, the intent in two lines, the mockup link, milestones, targets with their test tiers, risks, assumptions, open waivers. Later risky actions (installs, migrations, publishing) still get their own approval.
8. On approval: `gw gate G1 --approve "<the user's exact words>"`. It also marks P6 done. The approval is the user's answer to this packet: the request that started the work does not approve its plan. In an existing project, each change gets its own approval; G1 records the change it approved.

Until G1 is approved, the pre-edit hook blocks source edits at standard/large; docs, tests and `.groundwork/` stay editable.
