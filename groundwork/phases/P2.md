# P2: Target platform & stack

Decide **where the software runs** and **what it is built with**, checked against what this machine can do (`gw doctor` → Targets table).

## Questions (ask only what is still unknown)
1. On what do users use it: phone, desktop, browser, server, a device, a terminal?
2. Targets (multi-select): `web, backend, android, ios, windows, macos, linux-desktop, cli, embedded, game, browser-extension`. Each has a pack in `groundwork/packs/`.
3. How it is distributed: Play Store, App Store, MS Store/winget/MSI, Flathub/AppImage/deb, web hosting, a Docker image, a package registry, OTA firmware.
4. Device features needed: offline, push, background work, camera, GPS, BLE, USB/serial, GPU.
5. Which stack the user or team already knows. Prefer it.
6. Constraints: licence, budget, data residency, compliance.
7. Hosting and external services: cloud (AWS, Azure, GCP, Vercel, Cloudflare…), backend-as-a-service (Supabase, Firebase), payments (Stripe). These decide which vendor-specific skills are suggested.

## Choosing a stack
- If code exists, detect the stack from marker files (each pack lists `stacks.<id>.detect`). Don't switch stacks without a strong reason and user approval.
- Defaults when nothing exists:
  | Need | Default |
  |---|---|
  | web app | Vite + React + TypeScript (Next.js if SSR/SEO matters) |
  | backend | the team's language: FastAPI, Node (Hono/Fastify), Go, Spring, or .NET |
  | android only | Kotlin + Jetpack Compose |
  | android + ios | Kotlin Multiplatform + Compose if the team knows Kotlin/Android; Flutter (Dart); React Native/Expo if the team knows JS |
  | mobile + web + desktop, one codebase | Kotlin Multiplatform + Compose Multiplatform (Kotlin; native on Android, shared UI and logic), or Flutter (Dart) |
  | desktop on all OSes | Tauri (small binary); Electron if it needs the npm ecosystem |
  | windows-only business app | .NET WPF / WinUI 3 |
  | CLI | Go or Rust (single binary); Python if the team prefers it |
  | embedded | Zephyr / ESP-IDF / PlatformIO, depending on the board |
  | game | Godot (open source, CI-friendly); Unity or Unreal when the team already uses them |
  | browser extension | Manifest V3; WXT for several browsers |
- **One codebase for several targets.** When the targets span platforms (say Android, iOS, web and desktop), `gw set targets=…` lists the presets that cover all of them. Recommend one, chosen by the team's language, unless the user wants a native app per platform. `gw set preset=<kotlin-multiplatform|flutter|react-native|electron|tauri|dotnet-maui>` sets the targets and their stacks together; add `targets=<subset>` to take only some (`packs/presets.json`).
- **Tests and CI follow the targets, not the codebase.** Each target gets its own workflow with that platform's runner and tests (`gw ci write`, P8). Android runs on an emulator, iOS on a macOS simulator, web in a headless browser, desktop on each OS. A shared codebase still runs its tests on every target.
- **Feasibility check:** show the user which targets can be tested locally on this machine and which need CI (S3), using the doctor Targets table. Example: "iOS cannot be built on this Linux machine; the iOS UI tests will run on a macOS CI runner."

## Output
- `gw set targets=web,android stacks.web=vite-react stacks.android=flutter services=supabase,vercel`
- `docs/adr/0001-stack.md` from `templates/adr.md`: options considered, decision, consequences, and host constraints.
- `gw phase P2 done`.
